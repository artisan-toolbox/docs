# DataView redesign and demo plan

Make it easy to find a record, compare it with its neighbors, and tell what changed after a filter. Give developers the same search, filter, status, and navigation controls when they compose their own screen. This document records the design study, the implementation in the development checkout, and the remaining usability work.

**Try the proposal.** Open the [interactive Pressroom study](assets/data-view-design/study/index.html). Choose **Filters → Waiting** to see four matching tickets out of twelve. Clear the filter, activate **Reply due** to reverse the order, then switch to **List** to read the request. Change **Study layout** to **Sidebar** to compare both arrangements on the same records. [Desktop table](assets/data-view-design/study/wide-integrated.png) · [Phone list](assets/data-view-design/study/compact-integrated.png) · [Grid](assets/data-view-design/study/wide-grid.png)

**Recommendation.** Start with filters beside search. At 390 × 844 the integrated design placed the first ticket at y=282 px. The always-visible filters put it at y=408 px. At 1366 × 900 the integrated table had 220 px more width. Visible choices save an opening click for repeated triage, which makes a sidebar a good standalone example. These are measurements of layout. Testing time to find the right record requires people. The prototype uses native controls and local sample data. [Study notes and side-by-side alternatives](assets/data-view-design/study/README.md)

## The default composition

| Region  | Wide container                                                                                                                                                                         | Narrow container                                                                                                                                                              |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Header  | Optional title and one app action. On the next line, search followed by Filters. Put layout and advanced order controls at the trailing edge. Only applied criteria take a third line. | Give search and Filters the first available row. Let search take its own row when labels need room. Keep Filters and Sort reachable with a thumb. Collapse secondary actions. |
| Content | Start at the same leading edge as search and the footer summary. Use one separator between the tools and results. Keep existing rows readable during a refresh.                        | Size to the embed, including docs frames and side panels. Scroll a wide table locally and show an edge cue. List and grid reflow in place.                                    |
| Footer  | One sentence describing these results on the left. Page size, when configurable, and navigation on the right.                                                                          | Wrap summary above navigation. Use compact controls. Put direct page entry in a secondary action when available.                                                              |

Use the host typography, Web Awesome semantic text, surface, border, spacing, radius, and focus tokens. Align labels with their data and right-align comparable numbers and dates using tabular digits where appropriate. Use a quiet header background, one rule between rows, and a single accent for an active action. Status color always has a text label. The shell owns outer spacing and separators. Each control owns its label, focus ring, and internal padding. Empty regions leave no rule or gap. Use container queries based on when the content collides. A phone viewport and a narrow panel on a desktop should make the same decisions.

**Table.** Make the full sortable label area a target. Show a quiet sort affordance before activation and a distinct direction arrow after acceptance. Keep the icon's space stable. Plain headers have no button. Only the primary accepted sort receives `aria-sort`; announce priority and direction for additional terms. Preserve the configurable modifier, direction cycle, source tie-breakers, presets, and both header slot contracts. The Sort panel offers field, direction, priority, and removal on touch or keyboard. Expose only supported choices. Preserve numeric direction values for slot authors. [WAI sortable table example](https://www.w3.org/WAI/ARIA/apg/patterns/table/examples/sortable-table/)

**List.** Use a continuous list with dividers. Lead with the record title, follow with one useful sentence and the identifying metadata. Align the status and deadline at the far edge on wide layouts and below the title on small ones. The row action has its own focusable target. A one-column list should be usable without a title bar, toolbar, or pager.

**Grid.** Give each item one visual frame, a predictable title position, visible status, and an aligned foot for secondary facts. Images earn space when identifying the record matters. Use a single column where a second card would truncate the identifying text. Demonstrate a public `Card` slot and a custom content slot without double padding or borders. Preserve the existing list/grid item slots and row-key behavior. Switching layout is local. A user-selected view survives resizing and pending reads.

**Filtering.** Show global search when the handle offers it. Filters opens a field chooser with meaningful labels. A short finite set can use choices, a longer set a Select, and an authorized multiple selection a multi-select. A typed search editor offers only the advertised operators. Give text search its existing debounce or explicit-apply semantics. Keep draft edits local until their documented commit action. After success, show a removable value such as “Status: Waiting”. A rejected edit leaves the accepted rows and chip intact and the error beside the field. Restore focus on dismiss. Reserve wholesale reset for an explicit action that names its scope. Clearing a filter preserves independent searches, ordering, and other filters.

On a wide container, anchor the filter editor to its trigger. On a narrow container, give a multi-field editor a labeled dialog with a scrollable body and reachable apply action above the software keyboard. Escape or Cancel dismisses the draft. A single status choice can stay in a short anchored panel, as in the study. Before adding either presentation, try the public Popover and Dialog wrappers with actual Web Awesome inputs, nested selects, touch, and focus restoration.

**Pagination and status.** The public Core `Pagination` wrapper fits offset results with an accepted page, exact matching count, and a jump capability. Bind its `total` to matching records, `page-size` to the accepted page size, and `page` to the accepted one-based index. Use the cancelable before-change event to dispatch one Dapter operation. On failure retain the previous page. The wrapper supplies its own navigation landmark. Keep page entry, size changes, reload, and first/last where supported, with secondary placement. [Web Awesome pagination](https://webawesome.com/docs/components/pagination/)

| Accepted result                                             | Example footer copy                       | Navigation                                                                                                          |
| ----------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Offset, 10 on page 2, 30 matching of 300 authorized records | “11–20 of 30 matches · 300 total”         | Numbered pages, compact when narrow                                                                                 |
| Offset, unfiltered with a partial final page                | “21–23 of 23 records”                     | Disable Next. A single page needs only the summary and applicable settings.                                         |
| Simple, count unknown                                       | “10 records on this page”                 | Previous and Next when supported. Show current page only if known.                                                  |
| Cursor with an exact 30 matches                             | “10 on this page · 30 matches”            | Traverse available cursors. The exact count cannot provide a jump target.                                           |
| Infinite or bounded window                                  | “10 records in view”                      | Load more, loading, retry, exhausted, or restart as the handle permits. A bounded window can discard older records. |
| Empty source or no matches                                  | “No records yet” or “No matching records” | Offer a relevant recovery, such as removing the active filter. Preserve available settings.                         |

Compute ranges only from accepted offsets and actual returned rows. Use localized plurals and number formatting. Distinguish zero, unknown, and loading. “Total” is scoped to the authorized source. All controls read the existing handle. Rendering status must issue zero additional reads or count queries.

## Modular public contract

Front Awesome owns the Vue presentation. Dapter owns authorization, available operations, requested state, acceptance, counts, cursor tokens, and recovery. Today the DataView entry exports one runtime component. The toolbar, pager, and criteria editors are private. Start with the public controls that have an independent task. Promote an existing implementation after giving it a usable standalone contract.

| Proposed export or composition            | Independent use and acceptance                                                                                                                                                                                                                                              |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DataViewSearch` and `DataViewFilter`     | Pass a borrowed adapter. A named field/filter pair or a global filter selects one advertised capability. Each control gets an accessible label and usable default size. Place the filter in a sidebar next to a separate DataView. A change updates both through one owner. |
| `DataViewStatus` and `DataViewPagination` | Render status in a page heading, or render navigation alone below a custom list. The built-in footer composes those same pieces. Replacing navigation must let the app own the complete pagination area without duplicate counts.                                           |
| Header, results, footer                   | Keep the existing DataView entry for the default composition. Test a table with no surrounding chrome, a query-only bar, and a pager-only footer. Prefer existing slots. Add an opt-out or a region slot only where current contracts cannot express the composition.       |

Preserve the borrowed adapter and explicit context paths. `#toolbar` and `#pagination` replace their default contents. `#filters`, `#actions`, and `#footer` add content. Existing layout switching still works with a custom toolbar. `#header-ID` takes precedence over `#head-ID`. Keep controlled view/selection events, row-key identity, grouping across consecutive loaded records, and independent views sharing one owner. A control embedded in a host form must not submit that form. A removed or newly unauthorized capability clears its local draft and does not issue a request.

The first release can cover field/global search, accepted operators, finite scalar or enum choices, all/any search, source order, order presets, and multi-order using existing Dapter contracts. A public filter must distinguish `null`, `false`, `0`, `"0"`, the empty string, and a space. Preserve empty-selection Clear/Reject and numeric input validation. Reuse each field's existing dispatch and author-provided labels. Test that an older response cannot replace a newer choice. An arbitrary date range, facet count, or batched multi-field Apply would require its own evidence and capability contract. Keep those out of the redesign's critical path. A visual component cannot grant a new query operation.

### Definition of done

- **Responsive and visual.** Capture 320, 390, 768, and 1440 px viewports plus a 284 px embed on a wide screen. Include light/dark, long translated labels, 200% text, 400% browser zoom, RTL where supported, and reduced motion. Inspect the screenshot and the actual keyboard path. No clipped actions, stacked borders, overlap, accidental page scroll, or invisible sort direction. Keep table scrolling confined to the table. [WCAG reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- **Accessible.** Keep table/header associations and list semantics. Test Tab, Shift+Tab, Enter, Space, Escape, and visible focus after updates. Test VoiceOver on Safari and a desktop screen reader on the primary sort, multi-sort, filters, pagination, and error recovery. Give individual controls a 24 × 24 CSS px minimum target or applicable spacing exception. Aim for 44 × 44 for frequent touch controls. Verify text and focus contrast in both themes, plus forced colors. Announce each accepted result change once. [WCAG target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- **Usability.** Recruit five representative operators for a formative round, including people who use touch and keyboard. Use equivalent datasets and counterbalance old/new order. Ask them to find the next waiting ticket, compare two deadlines, reverse and add a sort, clear just one filter, and explain the filtered and total counts. Record completion without prompting, wrong answers, first wrong turns, and time per task. Proposed release gate: at least four of five complete each task unaided and nobody acts on the wrong record or scope. Fix and repeat any failed task. Ask two Laravel/Vue developers to reproduce the standalone-filter demo from public documentation alone. These are planned checks, not study results.
- **Product states.** Exercise first load, refresh with existing rows, empty source, zero matches, recoverable read error, unauthorized capability, pending or failed action, end of data, and expired cursor. Keep selection scope explicit, including “all loaded rows”. Verify independent handles stay independent.
- **Package validation.** Run Front Awesome `npm run check`, `npm test`, `npm run test:browser`, `npm run build`, and `composer quality:check`. In docs run `npm run demos:check`, `npm run dapter:demos:check`, the DataView and affected Dapter browser scripts, frontend and PHP tests, types, and production build. Recheck Core and any claimed Pro integration using the actual edition. If a Dapter public contract changes, run its package suite, cross-driver tests, old/new consumer matrix, and Boost discovery. Update the affected package skill and changelog with implementation.

The installed Front Awesome `frontend-design` and `webawesome-design` skills already cover visual direction, tokens, hierarchy, and composition. The Dapter implementation skill and demo checker already own capability coverage. Keep the DataView-specific decisions and acceptance matrix here. Promote them into contributor guidance after the first implementation passes on the actual package.
