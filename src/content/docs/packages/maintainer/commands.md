Open the interactive menu:

```bash
vendor/bin/maintainer
```

The menu displays the running Maintainer version beside its terminal banner and lists the available maintenance workflows. Interactive input is required. Run a command directly when automation or a specific workflow does not need the menu.

## Git commits

Create a commit from the current working tree:

```bash
vendor/bin/maintainer commit
```

Before selecting files, Maintainer offers to open the HTML diff workflow in the browser. The searchable multi-select then lists modified, staged, deleted, renamed, and untracked files, with every file selected by default.

Selected files replace the current staging-area selection and are staged with their complete working-tree contents. Previously staged files that are not selected remain in the working tree but are unstaged, preventing accidental inclusion.

Commit messages can be written manually in a multiline editor, generated by AI from the selected status and diff, or generated from that diff plus additional user context. AI messages follow Conventional Commits.

After Git creates the commit, Maintainer offers to push `HEAD` to `origin`. Pushing is disabled by default and always requires confirmation.

The commit workflow requires interactive input. When AI is selected, configure `ai.providers.commit_message` and its matching credentials first.

## Code quality

Run Pint, Rector, PHPStan, and Pest in sequence:

```bash
vendor/bin/maintainer quality
```

Maintainer runs the binaries installed by the consuming project and explicitly passes that project's configuration file to each tool. The isolated dependencies bundled in the Maintainer PHAR are never used to analyze, modify, or test the consuming project.

The workflow recognizes:

- `pint.json`;
- `rector.php`;
- `phpstan.neon`, `phpstan.neon.dist`, or `phpstan.dist.neon`;
- `phpunit.xml` or `phpunit.xml.dist` for Pest.

PHPStan receives `quality.phpstan.memory_limit` as an explicit `--memory-limit` argument. The default is `2G`; valid project values include `512M`, `4G`, a byte count, or `-1` for unlimited memory.

Install the tools in the consuming project before running the workflow. Constraints should follow that project's supported PHP and Laravel versions:

```bash
composer require --dev laravel/pint rector/rector driftingly/rector-laravel larastan/larastan pestphp/pest
```

When configuration is missing, an interactive run offers to create a recommended template. Pint uses a shared Laravel preset. Rector, PHPStan, and Pest ask whether the project is a Laravel application or package because their source and test paths differ. Maintainer suggests the type inferred from `composer.json`, but the selection remains explicit. Existing files are never overwritten.

In non-interactive and continuous integration environments, missing configuration stops the workflow and identifies the required file. The workflow stops at the first failing tool and returns its exit code.

After every tool succeeds, an interactive run inspects the Git working tree and offers to continue into the commit workflow when changes exist. Continuous integration never receives this prompt and never creates a commit.

## HTML Git diffs

Generate a comparison between `HEAD` and the working tree, then open it in the default browser:

```bash
vendor/bin/maintainer diff:html
```

Pass one Git reference to use it as the base for a working-tree comparison, or two references to compare them directly:

```bash
vendor/bin/maintainer diff:html main
vendor/bin/maintainer diff:html v1.0.0 v1.1.0
```

Reports are written to the operating system's temporary directory by default. Select a path or prevent the browser from opening with:

```bash
vendor/bin/maintainer diff:html main --output=artifacts/main-diff.html --no-open
```

Working-tree comparisons include staged and unstaged changes to tracked files. Add new files to Git before generating the report when they should be included.

Reports load the pinned `diff2html` 3.4.56 assets from jsDelivr when opened. Set `git.diff.output_format` to `line_by_line` or `side_by_side` in `maintainer.json` to control the layout:

```json
{
  "git": {
    "diff": {
      "output_format": "side_by_side"
    }
  }
}
```

## GitHub releases

Create a release for the consuming project:

```bash
vendor/bin/maintainer release:create
```

Before starting, the command requires:

- a completely clean Git working tree;
- a major branch named `0.x`, `1.x`, `2.x`, and so on;
- a class directly in a production PSR-4 namespace that implements `Versionable`;
- authenticated GitHub CLI access;
- a supported semantic version when the version constant already exists.

Other branch names and detached `HEAD` states abort the workflow. The branch determines the release major, and major increments are never offered within a branch.

Maintainer retrieves published GitHub releases, ignores drafts and unsupported tags, and selects the highest valid version for the branch major. It verifies that the selected release tag resolves locally and fetches a missing tag explicitly from `origin`, supporting shallow and `--no-tags` clones.

When `0.x` has no valid release, initial choices are `0.1.0`, `0.1.0-alpha.1`, and `0.1.0-beta.1`. Other majors start at `MAJOR.0.0` with equivalent prerelease choices.

### Version transitions

- A stable release may advance to the next patch, next stable minor, next minor alpha, or next minor beta.
- An alpha release may advance to the next alpha, first beta, or stable version with the same major, minor, and patch.
- A beta release may advance to the next beta or stable version with the same major, minor, and patch.
- Alpha and beta flows cannot create another patch or minor until their current version becomes stable.
- Major increments require the matching new major branch.

When the latest release is stable, Maintainer asks the provider configured under `ai.providers.release_type_suggestion` to recommend the next patch or stable minor version. Any fragment recommending a minor makes minor the consolidated default; otherwise patch remains the default. AI is not consulted when no prior release exists or a prerelease flow must finish. Provider or local-tag failures are reported while safely retaining the next patch as the default.

### Generated release content

After version selection, Maintainer:

1. writes the selected version;
2. runs the optional before-versioning callback;
3. builds release context from commits and the diff since the latest release;
4. generates release notes and validated changelog entries;
5. updates the version constant and managed README badge;
6. stages generated release files;
7. optionally opens an HTML review of the complete proposal;
8. creates a `chore(release): prepare VERSION` commit;
9. pushes it to `origin`;
10. publishes the GitHub release with `gh release create`.

Alpha and beta versions use GitHub's prerelease flag.

The changelog is created when absent. New releases are prepended and entries are grouped under Features, Fixes, Documentation, Refactoring, Performance, Tests, Build, CI, Maintenance, and other relevant categories.

Git remains the source of truth for changelog commit hashes. Invalid or unknown AI-generated hashes are ignored, and every real omitted commit receives a deterministic fallback entry derived from its Conventional Commit subject. A release with no commits since the selected base is rejected before AI is asked to generate content.

### AI context limits

Maintainer never sends an unbounded release diff to a provider. Source changes are divided into fragments of at most 24,000 characters, with at most 16 fragments analyzed. Generated output and dependency-heavy paths such as `builds/`, `dist/`, `vendor/`, `node_modules/`, coverage output, lockfiles, and minified assets are recorded as omitted instead of copied into prompts.

When the diff exceeds the fragment limit, Maintainer records that analysis was truncated and tells the user to review the remaining changes before accepting the version recommendation.

### Failure and termination behavior

Before a release commit is pushed, failures restore the repository to the captured starting `HEAD` and remove untracked release files.

On platforms exposing `SIGTERM` through `pcntl`, termination requests also restore the complete worktree when release content has been prepared but not pushed, then exit with status `143`. Once the push succeeds, Maintainer skips automatic rollback because reverting local files cannot safely undo remote state.
